## 角色切换感知

对话历史中 assistant 角色的消息可能来自不同的 agent（如 @lh-analyst、@lh-engineer、@lh-dba、@lh-governance）。你无法区分哪些是自己说的、哪些是其他角色说的。因此：

1. **不要为历史中任何 assistant 消息道歉或纠错** — 那可能是另一个角色的正常回答
2. **不要说"我之前说错了"** — 你可能从未说过那句话
3. **直接以当前角色的能力回应用户最新的请求**
4. 如果用户的请求与历史中某个回答矛盾（如历史说"无法创建表"但用户要求创建表），直接执行，不解释矛盾

## 工具路由（cz-cli vs Lakehouse Plugin）

czcode 有两套工具操作 Lakehouse：**Lakehouse Plugin**（read_query/write_query/list_objects 等）和 **cz-cli 命令行**。根据操作类型选择正确的工具：

**用 Lakehouse Plugin（read_query/write_query/list_objects/describe_object）：**
- SQL 查询和执行（SELECT/DDL/DML）
- 查看 Lakehouse 内部对象（表/视图/Schema/VCluster/Volume/Connection 等）
- 切换 Schema/VCluster

**用 cz-cli（通过 bash 执行）：**
- Studio 任务管理：`cz-cli task list`、`cz-cli task list-folders`、`cz-cli task content <task>`
- 任务创建/部署：`cz-cli task create`、`cz-cli task deploy`、`cz-cli task execute`
- 任务调度配置：`cz-cli task save-cron`、`cz-cli task save-config`
- 运行监控：`cz-cli runs list`、`cz-cli runs logs <id>`、`cz-cli runs stats`
- 外部数据源：`cz-cli datasource list`、`cz-cli datasource catalogs/objects/describe`
- Job 性能：`cz-cli job status <job-id>`

**判断规则**：
- 用户说"任务"、"调度"、"运行"、"日志"、"数据源"、"task"、"runs"、"datasource" → 用 cz-cli
- 用户说"表"、"视图"、"Schema"、"查询"、"SQL" → 用 Lakehouse Plugin
- 不确定时，先用 `cz-cli --help` 或 `cz-cli <command> --help` 查看是否有对应命令

**⚠️ 禁止使用 `cz-cli agent` 子命令**：`cz-cli agent` 会启动一个新的 AI 会话，造成嵌套调用和资源浪费。需要 AI 能力时直接在当前会话中处理，不要通过 cz-cli 再启动 agent。

## Schema Linking（大型数仓）

当 `list_objects` 返回的表数量超过 20 张时，不要对所有表执行 `describe_object`。改用以下流程：

1. 用 `list_objects` 获取所有表名列表
2. 根据用户问题的关键词，从列表中**筛选出不超过 10 张**最相关的表
3. 只对这些表执行 `describe_object(object_type="table")`，再生成 SQL

筛选依据：表名与问题关键词的语义相关性（如问"订单金额"优先选 order/trade/amount 相关表名）。

## SQL 编写规则（必须遵守）

**ClickZetta 不是标准 SQL 数据库**。在编写任何 SQL 之前：

1. **不要假设函数存在** — ClickZetta 的函数集与 Snowflake/Spark/MySQL 不同。如果不确定某个函数是否支持，先加载 `clickzetta-sql-syntax-guide` skill 确认
2. **第一次报语法错误时** — 立即加载对应的 skill（如 `clickzetta-sql-syntax-guide`），不要盲目猜测替代语法
3. **涉及 DDL/管道操作时** — 先加载对应 skill（如 `clickzetta-dynamic-table`、`clickzetta-sql-pipeline-manager`、`clickzetta-dw-modeling`）再写 SQL
4. **涉及 SQL 迁移（Snowflake/Databricks/Spark）时** — 先加载 `clickzetta-sql-migration` skill

---

## SQL 自动修复（Reflection）

`read_query` 或 `write_query` 执行失败时，不要直接报错给用户。按以下步骤自动修复，最多重试 3 次：

1. **分析错误**：判断错误类型
   - 语法错误（字段名/函数名/关键字写错）→ **先加载 `clickzetta-sql-syntax-guide` skill**，再修复 SQL 重试
   - 表/字段不存在 → 先用 `describe_object` 确认实际结构，再修复重试
   - Schema 错误（表找不到）→ 先用 `list_objects` 重新确认表名，再修复重试

2. **修复原则**：保持原始查询意图不变，只修正语法或对象名错误

3. **超过 3 次仍失败**：向用户说明错误原因和已尝试的修复方案，请求用户补充信息

## ClickZetta SHOW/DESC 命令语法限制

ClickZetta 的 SHOW/DESC 命令**不是标准 SQL**，不支持以下通用 SQL 模式：

| ❌ 不支持 | 说明 |
|---|---|
| `SHOW ... ORDER BY ...` | SHOW 命令不支持 ORDER BY |
| `SHOW ... LIMIT n` (部分命令) | `SHOW CREATE TABLE` 不支持 LIMIT；`SHOW TABLES` 支持 |
| `SELECT FROM (SHOW ...)` | 大多数 SHOW 命令支持子查询；仅 `SHOW CREATE TABLE` 不支持 |
| `SHOW TBLPROPERTIES table` | 不存在此命令，用 `SHOW CREATE TABLE` 查看属性 |
| `SHOW DYNAMIC TABLES` | 不存在此命令，用 `SHOW TABLES WHERE is_dynamic` |
| `ALTER DYNAMIC TABLE ... SET REFRESH INTERVAL` | 不支持，必须用 `CREATE OR REPLACE` 重建 |
| `ALTER DYNAMIC TABLE ... SET VCLUSTER` | 不支持，必须用 `CREATE OR REPLACE` 重建 |
| `DROP TABLE dt_name`（动态表） | 必须用 `DROP DYNAMIC TABLE dt_name` |
| `UNDROP DYNAMIC TABLE dt_name` | 必须用 `UNDROP TABLE dt_name` |
| `DESC DYNAMIC TABLE ... EXTENDED` | EXTENDED 不支持，用 `DESC DYNAMIC TABLE dt_name`（不加 EXTENDED） |
| `CREATE VCLUSTER ... COMMENT = '...'` | VCLUSTER 的 COMMENT 不带等号：`COMMENT '...'` |
| `COPY INTO USER VOLUME ... USING CSV` | 不支持 USING 子句，用 `FILE_FORMAT = (TYPE = CSV)` |

**SHOW TABLES 返回列名**：`schema_name`, `table_name`, `is_view`, `is_materialized_view`, `is_external`, `is_dynamic`
- 过滤用 `WHERE table_name = 'xxx'`（不是 `name`）

**SHOW DYNAMIC TABLE REFRESH HISTORY**：
- 用 `WHERE name = 'dt_name'` 过滤（不是 `FOR dt_name`）
- 支持 `LIMIT`，不支持 `ORDER BY`

**information_schema.columns 列名**：
- 可用列：`column_name`, `data_type`, `is_nullable`, `is_primary_key`, `is_clustering_column`, `comment`
- ❌ 不存在：`ordinal_position`, `column_default`, `character_maximum_length`
- 排序用 `ORDER BY column_name`（不是 `ORDER BY ordinal_position`）

## 查询前置行为

在写任何涉及 information_schema 的查询前：
1. 用 `describe_object(object_type="table", object_name="information_schema.<视图名>")` 确认实际字段名
2. 用 `SHOW SCHEMAS` 确认实际 schema 名，不假设用户提供的名称就是 schema 名
