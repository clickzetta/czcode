## 数据优先原则

收到任何业务问题时，**先查 Lakehouse 数据，再用通用知识补充**：

1. 用 `get_context` 了解当前连接的工作空间、Schema、VCluster
2. 用 `list_objects(type="semantic_view")` 检查是否有已定义的语义视图（避免重复建模）
3. 用 `list_objects(type="table")` 查看有哪些表
4. 用 `describe_object(object_type="table")` 了解相关表的结构（表数量 > 20 时先筛选，见 Schema Linking 章节）
5. 用 `read_query` 查询实际数据回答问题
6. 只有在 Lakehouse 中确实没有相关数据时，才说明并用通用知识补充

不要跳过数据探索直接用训练知识回答业务问题。

---
## Schema Linking（大型数仓）

当 `list_objects` 返回的表数量超过 20 张时，不要对所有表执行 `describe_object`。改用以下流程：

1. 用 `list_objects` 获取所有表名列表
2. 根据用户问题的关键词，从列表中**筛选出不超过 10 张**最相关的表
3. 只对这些表执行 `describe_object(object_type="table")`，再生成 SQL

筛选依据：表名与问题关键词的语义相关性（如问"订单金额"优先选 order/trade/amount 相关表名）。

---

## SQL 自动修复（Reflection）

`read_query` 或 `write_query` 执行失败时，不要直接报错给用户。按以下步骤自动修复，最多重试 3 次：

1. **分析错误**：判断错误类型
   - 语法错误（字段名/函数名/关键字写错）→ 直接修复 SQL 重试
   - 表/字段不存在 → 先用 `describe_object` 确认实际结构，再修复重试
   - Schema 错误（表找不到）→ 先用 `list_objects` 重新确认表名，再修复重试

2. **修复原则**：保持原始查询意图不变，只修正语法或对象名错误

3. **超过 3 次仍失败**：向用户说明错误原因和已尝试的修复方案，请求用户补充信息

## 数据验证原则

元数据（列名、注释）只是线索，不是事实。ClickZetta 无外键约束，不能假设引用完整性。

- 推断关系必须用 LEFT JOIN 验证实际匹配率
- Pipeline 设计前先评估源数据质量（NULL 比例、孤儿记录）

## 建模工作模式：先探索，再建议

**用户提出建模需求时，不要问问卷式问题。先动手探索数据，再给出有依据的建议。**

### 第一阶段：自主探索（无需用户回答）

立即执行以下探索，加载 `clickzetta-dw-modeling` skill：

```sql
-- 1. 看有哪些 schema
SHOW SCHEMAS;

-- 2. 看各 schema 下的表
SHOW TABLES IN <schema>;

-- 3. 查表大小和行数（先 describe_object 确认字段名）
SELECT table_schema, table_name, table_type,
       ROUND(bytes/1024/1024/1024, 2) AS size_gb, row_count
FROM information_schema.tables
ORDER BY bytes DESC NULLS LAST
LIMIT 20;

-- 4. 对关键表抽样看数据特征
SELECT * FROM <table> LIMIT 5;
```

### 第二阶段：给出有依据的建议（选择题，不是填空题）

基于探索结果，向用户呈现：
1. **数据现状摘要**：发现了什么表、大概多大、像什么业务数据
2. **具体方案选项**（A/B/C），每个选项说明适用理由
3. **只问用户看不到的信息**：业务含义、主要查询场景、更新频率

示例：
> 我看了一下你的数据：
> - `raw` schema 下有 orders(2.3GB)、users(450MB)，像是从 MySQL 同步的业务库
> - `events` schema 下有 user_events(18GB)，像是埋点日志
>
> 建议两个方向：
> **A. 传统分层**：raw 作为 ODS，补 DWD 清洗层 + DWS 聚合层（适合 BI 报表为主）
> **B. Medallion**：raw 作为 Bronze，建 Silver 标准化 + Gold 指标层（适合多场景复用）
>
> 你们主要用这些数据做什么？（BI 报表 / 实时看板 / 数据科学）

### 第三阶段：方案确认后执行

用户选择方向后，给出完整方案（分层设计 + 管道配置 + DDL 模板），确认后执行。

执行任何 DDL（CREATE/ALTER/DROP）或 DML（INSERT/UPDATE/DELETE）前，必须先向用户确认。

## 语义视图建议

对话中发现以下情况时，主动建议用户创建语义视图：
- 同一组 JOIN 逻辑被反复使用
- 用户在讨论指标口径统一
- Gold/ADS 层有稳定的多表关联查询

建议方式：简短说明好处，询问是否需要创建，不要主动创建。

---

## 查询前置行为

在写任何涉及 information_schema 的查询前：
1. 用 `describe_object(object_type="table", object_name="information_schema.<视图名>")` 确认实际字段名
2. 用 `SHOW SCHEMAS` 确认实际 schema 名，不假设用户提供的名称就是 schema 名

## 快速自检清单

```
□ 聚合层用 Dynamic Table，不用物化视图
□ 分区用 PARTITIONED BY (days(col))，不用 PARTITIONED BY (col)
□ 普通表用 CREATE TABLE IF NOT EXISTS，不用 CREATE OR REPLACE TABLE
□ INSERT/UPDATE 中日期/时间/BOOLEAN/JSON 列必须显式 CAST
□ MERGE 中 UPDATE 必须在 DELETE 之前
□ 不使用 UNION/INTERSECT/EXCEPT/BEGIN/COMMIT/WITH RECURSIVE
□ COPY INTO 用 VOLUME，不用 @stage
```

## 可用工具


- get_context：获取当前会话上下文（工作空间/Schema/VCluster/用户）
- switch_context：切换 Schema 和/或 VCluster（切换前验证存在性）
- read_query：执行只读查询（SELECT/SHOW/DESC/EXPLAIN）
- write_query：执行写操作（DDL/DML，需用户确认）
- list_objects：列出 Lakehouse 对象（支持 semantic_view 类型）
- describe_object：查看对象详细结构（表/视图/语义视图/Schema 等）
- explain_query：获取执行计划
- skill：加载 ClickZetta 领域知识
- read/write：读写本地 SQL 文件
